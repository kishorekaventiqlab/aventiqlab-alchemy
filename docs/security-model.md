# 10. Security Model

## Principles

- Alchemy runs in its **own AWS account** (`880636108741`). Nothing in it is shared with the platform, ASTRA or Arena accounts.
- No hardcoded credentials anywhere. The CLI holds one service token; Lambdas use execution roles; the platform holds one service token.
- **Nothing is public.** Content is delivered only via short-lived presigned URLs minted by the API after a token check.
- Least privilege spelled out per principal, and asserted by tests (`packages/infra/test/alchemy-stack.test.ts`).

## Principals and what they can do

| Principal | Credential | Can | Cannot |
|---|---|---|---|
| **AventiqLab platform** (Amplify Lambda) | READ token, `Authorization: Bearer` | every `GET` | any write; see drafts; reach S3/DynamoDB directly |
| **Publishing CLI** (desktop) | PUBLISH token | every route; PUT to presigned URLs | reach S3/DynamoDB directly; delete anything; change published versions |
| **Authorizer Lambda** role | IAM | `secretsmanager:GetSecretValue` on the two token secrets | anything else |
| **API Lambda** role | IAM | `dynamodb:GetItem/Query/PutItem/DeleteItem/BatchWriteItem/ConditionCheckItem` on the table + its indexes; `s3:GetObject/PutObject` on `bucket/*` | `Scan`, `UpdateItem`, `s3:ListBucket`, `s3:DeleteObject`, anything on other resources |
| **Deployer** (`alchemy-developer` profile) | IAM user in the Alchemy account | `cdk deploy` | is a human, not used at runtime |

The brief asked for separate roles for "Lambda execution, Publishing, S3 access, DynamoDB access". In this
design the *publishing* role and the *S3/DynamoDB access* role collapse into the API Lambda's role on
purpose: the CLI never gets AWS credentials, so there is no second principal that needs them
(**decision**). Read vs publish is separated at the **token** level instead, which is the boundary the
platform actually crosses.

## Token handling

- Two 48-char tokens generated by Secrets Manager at deploy (`alchemy/{stage}/read-token`, `alchemy/{stage}/publish-token`), `RETAIN`.
- The authorizer compares SHA-256 digests with `timingSafeEqual`; tokens shorter than 16 chars are rejected outright.
- Read tokens receive a gateway policy for `GET/*` only; publish tokens for `*/*`. The service re-checks scope on every mutation (defence in depth).
- Authorizer cache 5 min per token value.
- **Rotation:** put a new value in the secret; the authorizer picks it up within 5 minutes; update the consumer. Dual-token grace periods are not implemented (add a second secret per scope when needed).

## Data protection

| Store | At rest | In transit | Public access |
|---|---|---|---|
| S3 | SSE-S3 AES-256 | bucket policy denies non-TLS | Block Public Access ×4, BucketOwnerEnforced |
| DynamoDB | AWS-managed key, PITR on, deletion protection on | TLS | n/a |
| Secrets Manager | KMS (AWS-managed) | TLS | n/a |
| API Gateway | — | TLS 1.2+ regional endpoint | `/health` only |

Presigned GETs: 15 min default, hard-capped by `ALCHEMY_SIGNED_URL_TTL_SEC` (≤ 1 h). Presigned PUTs: 1 h,
Content-Type pinned in the signature. Both are scoped to a single object key.

Bucket CORS allows `GET, HEAD` only from `alchemy:allowedOrigins` (default: the aventiqlab.com apex + www +
localhost:3000). Add the platform's `*.amplifyapp.com` origin in `packages/infra/cdk.json` before deploy.

## Logging and audit

- CloudWatch Logs for both Lambdas and API Gateway access logs (JSON standard fields), 30-day retention.
- Every lifecycle transition is a `PUBLICATION` row with `actor`, and is appended to the version's `statusHistory`.
- `_publication.json` beside each published version records what was verified.
- S3 versioning provides object-level history.

## Rate limiting

Stage throttle 50 rps / burst 100 for the whole API. Enough for a catalog API; revisit with usage plans if
per-consumer limits are needed.
